## 1. 관리자 열람 — ★ **열람 쪽을 만들지 않습니다**

가장 중요한 결정입니다.

받은 자료를 운영자가 보려면 보통 「관리자 쪽」을 만듭니다.
그런데 **그 쪽 자체가 새 구멍**입니다 — 주소가 알려지면
개인정보가 통째로 샙니다. 암호를 걸어도 그 암호가 또 관리
대상이 되고, 오늘 물때 암호에서 겪었듯 **코드에 박히면
공개 저장소로 흘러갑니다.**

**그래서 열람 쪽을 안 만듭니다.**

```
운영자가 보는 법
  파일질라(FTP) 로 data-private/club/2026-10.jsonl 을
  내려받아 **내 컴퓨터에서** 엽니다.
```

| | 열람 쪽을 만들면 | 내려받아 보면 |
|---|---|---|
| 새 공격면 | **생깁니다** | 없습니다 |
| 암호 관리 | 하나 더 | 이미 있는 FTP 뿐 |
| 샐 경로 | 주소 유출·세션 탈취·권한 버그 | FTP 계정뿐 |
| 불편함 | 없음 | **조금 있음** |

문의가 하루 몇 건인 사이트입니다. **조금 불편한 쪽이 맞습니다.**
문의가 늘어 손이 모자라면 그때 다시 의논합니다.

★ 그러므로 **관리자 인증 장치가 필요 없습니다.** 만들지 않는
  것이 이 항목의 답입니다. 인증을 안 만드는 대신 **FTP 계정
  보호가 유일한 열쇠**가 되므로, 그 계정 암호는 지금처럼
  주인·감독실만 다룹니다.

## 2. HTTPS 와 접근 기록

### HTTPS
사이트는 이미 전부 HTTPS 입니다. 폼도 같은 자리에 있으므로
**따로 할 일이 없습니다.** 다만 받는 쪽에서 한 번 더 봅니다.

```php
// http 로 들어오면 받지 않습니다
if (empty($_SERVER['HTTPS']) && 
    ($_SERVER['HTTP_X_FORWARDED_PROTO'] ?? '') !== 'https') {
    // 400 으로 돌려보냅니다
}
```

★ 호스팅이 앞단에서 TLS 를 끊는 구조면 `$_SERVER['HTTPS']` 가
  비어 있을 수 있어 `X-Forwarded-Proto` 도 함께 봅니다.
  **올리기 전에 서버에서 그 값을 한 번 찍어 확인**해야 합니다 —
  짐작으로 두면 멀쩡한 접수가 전부 막힙니다.

### 접근 기록 — ★ **우리는 따로 남기지 않습니다**

접수 자체의 기록을 우리가 남기면 **IP·시각이 또 하나의
개인정보**가 됩니다. 10-13 문서 3절에서 「IP·UA·리퍼러는 안
담는다」고 정했는데, 기록을 따로 두면 그 약속이 뒤집힙니다.

```
우리가 남기는 것   받은때 · 동호회 칸들 (그뿐)
서버가 남기는 것   웹서버 접근 로그 (호스팅 기본, 우리 소관 밖)
```

★ 호스팅 기본 로그에는 IP 가 남습니다. **그것은 우리가 만드는
  것이 아니고 끌 수도 없습니다.** 개인정보 방침(`privacy.html`)에
  그 사실이 적혀 있는지 **확인이 필요합니다** — 안 적혀 있으면
  한 줄 보태야 합니다. (확인만 하고 아직 안 고쳤습니다)

### 이상한 접근을 알아채는 법
기록을 안 남기는 대신, **자료 파일 자체로** 봅니다.

- 한 달 파일이 갑자기 커짐 → 10-13 문서 4절의 1MB 상한이 막음
- 같은 내용이 여러 번 → 받은때로 눈에 띔
- 「안 받는 것」이 적혀 들어옴 → **발견 즉시 그 줄을 지웁니다**

## 3. 보관 기간과 **파기**

기간은 정해져 있습니다 — **6개월**(10-13 문서 5절, 동의 문구에
적힌 그대로). 빠진 것은 **어떻게 지우느냐**입니다.

```
파일이 달마다 하나입니다 — data-private/club/2026-10.jsonl
  ⇒ 6개월이 지난 달 파일을 **통째로 지웁니다.**
```

| | |
|---|---|
| 누가 | 운영자(주인 또는 감독실) |
| 언제 | 달이 바뀔 때. 2026-10 파일은 **2027-04** 에 지웁니다 |
| 어떻게 | 파일질라로 그 파일 하나를 지웁니다 |
| 확인 | 지운 뒤 폴더 목록으로 없어진 것을 눈으로 봅니다 |

★ **자동 삭제를 넣지 않습니다.** 지우는 코드가 잘못되면
  **되돌릴 수 없습니다.** 한 달에 한 번, 사람이 파일 하나를
  지우는 편이 안전합니다. 자료가 쌓여 손이 모자라면 그때
  다시 의논합니다.

★ 중간에 **지워 달라는 요청**이 오면 그 줄만 지웁니다. 파일이
  한 줄에 하나(JSONL)라 **그 줄만 지우면 끝**입니다 — 이것이
  이 꼴을 고른 까닭이기도 합니다.

## 4. 오류 대응 — 손님에게 무엇을 보여 주나

★ **「실패했습니다」로 끝내지 않습니다.** 손님이 적은 글이
  사라지면 다시 안 씁니다. 떠납니다.

| 무엇이 | 손님에게 | 속으로 |
|---|---|---|
| 잘 받음 | 「받았습니다. 며칠 안에 연락드립니다」 | 한 줄 덧붙임 |
| 칸이 비었음 | **그 칸을 짚어** 알림. 적은 글은 **그대로 둠** | 안 받음 |
| 너무 긴 글 | 「○○는 ○자까지입니다」 · 글 그대로 둠 | 안 받음 |
| 1분 안에 또 보냄 | 「조금 뒤 다시 눌러 주세요」 | 안 받음 |
| 표(CSRF)가 안 맞음 | 「쪽을 새로 고치고 다시 보내 주세요」 | 안 받음 |
| 파일이 꽉 참 | **「지금은 받지 못합니다. ohjunhan@gmail.com 으로 보내 주세요」** | 안 받음·알림 |
| 서버 탈 | 위와 같은 안내 | 안 받음 |

★ **어떤 경우에도 손님이 적은 글을 지우지 않습니다.** 폼을
  다시 그리지 말고, 받은 값을 그대로 채워 돌려줍니다.
★ 막다른 길에서는 **메일 주소를 보여 줍니다.** mailto 링크를
  다시 두자는 것이 아니라, 접수가 막혔을 때 손님이 **갈 곳이
  있어야** 하기 때문입니다.
★ 속사정(파일 경로·PHP 오류)은 **손님에게 보이지 않습니다.**

## 5. 손댈 파일과 권한

| 파일 | 무엇 | 새로/고침 |
|---|---|---|
| `api/.htaccess` 또는 뿌리 `.htaccess` | `data-private/` 막기 | 고침 ★ |
| `api/club-apply.php` | 받는 자리 (약 90줄) | 새로 |
| `data-private/club/` | 자료 자리 | 새로 |
| `data/raw/site.json` | `받는곳` 한 줄 | 고침 |
| `engine/build.py` 또는 틀 | 폼 그리기 | 고침 |
| `privacy.html` 자료 | 접수 항목 한 줄 | 고침(확인 필요) |

**파일 권한**

```
data-private/           750   (웹서버가 들어가 쓸 수 있을 만큼만)
data-private/club/      750
data-private/club/*.jsonl  640
api/club-apply.php      644
```

★ 777 로 두지 않습니다. 호스팅이 어떤 사용자로 PHP 를 돌리는지에
  따라 750 으로 못 쓸 수 있는데, **그때 777 로 올리지 말고
  감독실에 물어야 합니다.** 쓰기가 안 되면 접수가 조용히
  실패하므로, 올린 직후 **한 건 넣어 보고 파일이 생겼는지**
  눈으로 봅니다.

## 6. 운영 위험 — 무엇이 잘못될 수 있나

| 위험 | 얼마나 | 막는 법 |
|---|---|---|
| **자료 폴더가 웹에 열림** | **치명** | 10-13 문서 1절 차례 — **막기를 먼저**, 빈 파일로 403 눈으로 확인한 뒤에 만듦 |
| `.htaccess` 를 고치다 **사이트 500** | **치명** | 규칙 27 — BOM 없이, 한 번에 하나, 올린 직후 응답 코드, 500 이면 **먼저 되돌림** |
| 쓰기 권한이 없어 **조용히 실패** | 큼 | 올린 직후 한 건 시험, 파일 생겼는지 확인 |
| 로봇이 쏟아부음 | 중간 | 1분 1회 · 1MB 상한 · CSRF |
| 민감정보를 손님이 적음 | 중간 | 「안 받는 것」 굵게 · 발견 즉시 그 줄 삭제 |
| 파기를 **잊음** | 중간 | 갱신 대장(`data/refresh-plan.json`)에 한 줄 — 「동호회 접수 파기 · 6개월 · 손」 |
| FTP 계정이 샘 | 큼 | 지금처럼 주인·감독실만. **팀은 받지 않습니다** |
| 접수가 막혔는데 **아무도 모름** | 중간 | 4절 — 손님에게 메일 주소를 보여 줌 |

★ 가장 큰 위험은 **차례를 거꾸로 하는 것**입니다. 만들고 나서
  막으면 **첫 접수부터 공개**됩니다.

## 7. 승인받아야 움직이는 것 (그대로입니다)

```
  ① .htaccess 에 막기 올리기        — 서버 설정 · 500 위험
  ② 빈 파일로 403 눈으로 확인
  ③ api/club-apply.php 올리기       — 서버 코드
  ④ data-private/ 만들기            — 개인정보 저장소
  ⑤ 받는곳 채워 접수 켜기           — 수집 시작
```

**오늘 한 것은 이 문서뿐입니다.** ①~⑤ 중 아무것도 하지
않았고, 로컬에도 `api/`·`data-private/` 를 만들지 않았습니다 —
만들어 두면 **실수로 올라갈 수** 있기 때문입니다.
