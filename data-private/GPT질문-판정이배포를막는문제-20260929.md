# 배포 판정(NO-GO)이 오픈을 지체시키는 문제 — 의견을 구합니다

2026-09-29 · 바다가자닷컴(badagaja.com) 재구축

---

## 0. 무엇을 물어보려 하는가

오늘 정식 오픈을 하려는데 **배포 판정에서 다섯 번 막혔습니다.**
판정 한 번에 12~13분이 걸려 **약 1시간을 썼습니다.**

사이트 주인이 「검수에 시간을 너무 소비한다」고 하십니다. 맞는 말씀입니다.

**묻고 싶은 것**
1. 판정 기준(NO-GO)을 낮추는 것이 옳은가, 아니면 다른 길이 있는가
2. 아래 제가 낸 세 가지 제안이 맞는 방향인가
3. 놓친 것이 있는가

## 1. 이 사이트가 어떤 것인가 (배경)

- 정적 사이트 416쪽. 전국 57권역의 **물때·낚시·해루질 포인트 3,603곳** 안내
- 자료가 매달 갱신됩니다. 그래서 **쪽을 손으로 고치지 않고 생성기가 만듭니다**
- 손님이 이 자료를 보고 **실제로 바다에 나갑니다.** 물때가 틀리면 위험합니다
- 이미 운영 중인 옛 사이트가 있고, 그것을 새 엔진으로 갈아 끼우는 중입니다

## 2. 지금 판정 구조

**검사기 28개**가 있고, 판정(`gate.py`)이 이를 묶어 한 줄 결론을 냅니다.

판정 상태 6가지: `PASS / FAIL / NOT_TESTED / ERROR / INFRA_FAIL / N.A.`
배포 상태 3가지: `GO 후보 / 검증 배포 필요 / NO-GO`

- **`GO 후보`** — 20번(서버 검증)까지 다 쟀다
- **`검증 배포 필요`** — 올리기 전에 잴 수 있는 것은 다 쟀고, **올려야만 잴 수 있는 항목(20번)만 남았다** → **올립니다**
- **`NO-GO`** — 그 밖 → **막습니다**

원칙은 **Fail-Closed**(모르면 PASS 아님)입니다.

### 깃허브 일꾼 둘

| 일꾼 | 언제 도나 | 시간 |
|---|---|---|
| **배포 판정**(`gate.yml`) | `git push` 하면 자동 | 12~13분 |
| **운영 배포**(`deploy.yml`) | **손으로 눌러야** 함 | 안에서 **판정을 다시 돌림**(12분) + 올리기 |

## 3. 오늘 실제로 일어난 일 (숫자)

| | |
|---|---|
| 판정 횟수 | 5번 (`#41`~`#45`) |
| 걸린 시간 | 각 12~13분 = **약 62분** |
| 그중 **같은 까닭**으로 막힌 것 | **3번** (`#41`·`#42`·`#43`) |
| 판정이 알려 준 **새 정보** | **2개** |

**정보 2개를 얻는 데 62분**을 썼습니다.

### 막은 것 네 가지

1. **`덧 사진`** — 축제 달력 쪽에 그림이 하나도 없음
   → 주인이 「표지 삽화는 정보 전달도 없고 칸만 차지한다」고 빼라 하셔서 뺐더니,
     그 쪽에 **보이는 것이 하나도 없어졌습니다**(사이트 규칙: 글만 있는 쪽은 안 됨).
   → 달마다 축제 수를 보여 주는 막대 그래프를 넣어 고쳤습니다.
   → 그런데 **설명이 「그림」으로 시작해야** 하는 규칙이 있어 또 막혔습니다
     (그림을 사진인 척하지 않게 하는 규칙. 촬영자를 지어내면 안 되므로)

2. **`2번 검사기 자기검증(뮤테이션)`** — 위 1번과 얽힘

3. **`4번 416쪽 전체 렌더링`** — **375px(휴대폰)에서 쪽 전체가 405px 로 넘쳐 가로 스크롤 발생**
   → 제가 오늘 넣은 배치(사진 왼쪽·수치 오른쪽) 탓.
     CSS 격자 칸이 기본 `min-width:auto` 라 안 줄어들었습니다.
   → **1280px(PC)에서는 멀쩡해서, 저는 화면을 찍어 보고 「좋아졌다」고 보고했습니다.**

4. **`20번 실제 서버 배포 후 검증`** — 올려야만 잴 수 있음(구조상 당연)

## 4. 제 판단

### ㉠ 판정은 제 일을 했습니다

**375px 가로 넘침은 진짜 탈**이었습니다. 손님의 절반 이상이 휴대폰입니다.
**판정이 없었으면 그대로 나갔습니다.** 제가 PC 화면만 보고 통과라 했으니까요.

### ㉡ 진짜 문제는 셋

**1) 제가 판정을 「검사 도구」로 썼습니다**

그 두 가지는 **로컬에서 몇 초~몇 분이면** 알 수 있었습니다.
그런데 저는 검사기를 **`--strict` 없이** 돌려 끝난값 0 을 보고
「모든 검사가 통과했습니다」라고 보고했습니다.
**판정은 `--strict` 로 돕니다.** 인자가 달랐습니다.

→ **40분은 판정 탓이 아니라 제 탓입니다.**

**2) 배포가 판정을 *또* 돌립니다**

push 때 12분, 배포 때 **다시** 12분. 같은 커밋인데 두 번입니다.

**3) 「막는 것」과 「알리는 것」이 안 갈려 있습니다**

- 「375px 에서 옆으로 밀림」 → **손님이 다칩니다.** 막아야 합니다
- 「그림 설명이 「그림」으로 시작하지 않음」 → **손님은 아무렇지 않습니다.**
  우리 표기 규칙일 뿐인데 **이것 하나로 배포가 멈췄습니다**

## 5. 제 제안 세 가지

| 무엇 | 왜 | 아끼는 시간 |
|---|---|---|
| **올리기 전 「한 줄 검사」** — 1분 안에 끝나는 검사 전부를 `--strict` 로 묶어 한 명령으로. 지금은 제가 손으로 골라 돌려서 빠뜨립니다 | 사람(저)이 인자를 빠뜨리는 것을 구조로 막습니다 | 판정 한 번(13분) |
| **배포가 판정을 다시 안 돌리기** — 같은 커밋의 판정 결과가 있으면 그것을 씁니다 | 같은 일을 두 번 합니다 | **매 배포 12분** |
| **판정을 두 층으로** — ① **막는 것**: 쪽이 안 뜸·가로 넘침·자료 404·물때 틀림 ② **알리는 것**: 표기 규칙·글자 차례 | 오늘 같은 헛걸음 방지 | 판정 두세 번 |

## 6. 제가 **반대**하는 것

**NO-GO 기준 자체를 낮추는 것에는 반대합니다.**

오늘 판정이 잡은 것이 진짜 탈이었고, 저는 그것을 놓친 채
「좋아졌다」고 보고했습니다. 기준을 낮추면 **저를 믿어야 하는데,
오늘 저는 세 번 틀렸습니다.**

1. `--strict` 를 안 붙이고 「통과」라 함
2. PC 화면만 보고 「좋아졌다」고 함
3. 고치다 다른 함수를 지움(생성기가 멈춰 바로 알았습니다)

**20번(서버 검증)은 지금도 옳습니다** — 「검증 배포 필요」로 올라가게 되어 있습니다.

    바뀐 쪽만 재는 것이 안전한가? 아니면 표본만?)
